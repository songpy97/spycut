# SpyCut V1 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build a Windows and macOS desktop application that opens a local H.264/H.265 MP4 recording, lets the teacher mark immutable delete intervals in original-time order, reviews every join, and exports a frame-accurate MP4 for later editing.

**Architecture:** Use a Tauri 2 modular monolith. Svelte/TypeScript renders the interface and uses the operating system WebView for preview; Rust is the sole source of truth for project state, interval rules, persistence, probing, export planning, process supervision, and output validation. FFmpeg and ffprobe run as supervised sidecars; V1 performs a single sequential decode, selects only kept frames, and emits one consistently re-encoded stream rather than attempting H.265 boundary smart rendering.

**Tech Stack:** Tauri 2, stable Rust, Svelte 5, TypeScript, Vite, pnpm, Vitest, Cargo test, serde/serde_json, tokio, tracing, blake3, FFmpeg/ffprobe, MP4 with H.264 or H.265 video and AAC audio.

## 1. Product definition

### 1.1 User problem

A source recording may be three hours long and several gigabytes in size. The teacher wants to remove mistakes, student-code inspection, private chats, waiting, and other non-public portions, leaving less than one hour for further work in a professional editor.

General-purpose editors expose movable clips on a ripple timeline. After many cuts, clips become fragmented and can be deleted, shifted, overlapped, or reordered accidentally. SpyCut removes that entire class of mistakes by not modeling movable clips at all.

### 1.2 Product promise

SpyCut is a non-destructive delete-interval marker and exporter:

1. Open one original MP4 without copying it.
2. Watch and navigate the original timeline.
3. Mark intervals that must not appear in the public result.
4. Review each resulting join.
5. Export an accurately cut MP4 in original chronological order.
6. Import that MP4 into a professional editor for subtitles, voice-over, titles, or other finishing.

### 1.3 V1 goals

- Support one local MP4 source per project.
- Support H.265/HEVC as the primary video codec.
- Support H.264/AVC as a compatible input codec.
- Play locally using HTML Video when the platform decoder supports the selected file.
- Mark, adjust, remove, undo, and redo delete intervals.
- Make interval bodies immovable and derive all kept intervals from the source timeline.
- Persist every accepted edit automatically.
- Review every join before export.
- Export at source-frame precision rather than keyframe precision.
- Prefer hardware-accelerated encoding and fall back explicitly when unavailable.
- Keep source data local and untouched.
- Remain responsive for multi-gigabyte, multi-hour files.

### 1.4 Explicit non-goals

V1 will not implement:

- Multiple source files in one project
- Reordering, dragging, or layering clips
- Ripple editing
- Transitions or effects
- Captions, transcription, voice-over, or AI analysis
- Waveform generation
- Full-video thumbnail strips
- Audio mixing, gain automation, noise reduction, or track selection
- Cropping, scaling, picture-in-picture, or annotations
- Cloud upload, accounts, collaboration, or telemetry
- Boundary-only H.265 smart rendering
- Proxy generation
- Linux support
- Live-stream capture

Anything on this list requires a new product decision rather than an incidental V1 addition.

## 2. Core domain rules

These are invariants, not UI preferences.

1. **The source file is immutable.** Open it read-only. Never rename, modify, truncate, or overwrite it.
2. **The source timeline is immutable.** Its zero point, duration, and chronological order never change.
3. **The only editable media object is a delete interval.** There is no movable `Clip` entity.
4. **A delete interval is half-open:** `[start_us, end_us)`. The start is deleted; the end is retained.
5. **All time values use signed 64-bit microseconds in Rust.** JavaScript receives safe numeric values; a three-hour project is far below JavaScript's integer precision limit.
6. **Intervals are normalized after every command.** Clamp to the media duration, sort, and merge overlaps or exact adjacency.
7. **Kept intervals are derived.** They are the complement of normalized delete intervals over `[0, duration_us)` and are never independently edited or persisted as source of truth.
8. **Export order is derived from original time.** No command or persisted field can change it.
9. **An export uses an immutable snapshot.** Editing is locked while a job runs. Cancellation returns to the same reviewed snapshot.
10. **An empty result is not exportable.** If all source time is deleted, show a clear validation error.
11. **Source identity is verified before playback resume and before export.** A changed source must be relinked or reopened explicitly.
12. **Every destructive-looking UI action is reversible.** Deleting a marker means removing the deletion instruction, not deleting media.

### 2.1 Canonical model

```rust
pub type Micros = i64;

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub struct DeleteInterval {
    pub id: u64,
    pub start_us: Micros,
    pub end_us: Micros,
}

#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct SourceIdentity {
    pub canonical_path: String,
    pub size_bytes: u64,
    pub modified_unix_ms: i64,
    pub edge_hash_blake3: String,
}

#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct ProjectV1 {
    pub schema_version: u32,
    pub project_id: String,
    pub source: SourceIdentity,
    pub media: MediaInfo,
    pub delete_intervals: Vec<DeleteInterval>,
    pub next_interval_id: u64,
    pub last_playhead_us: Micros,
    pub reviewed_interval_ids: Vec<u64>,
    pub created_unix_ms: i64,
    pub updated_unix_ms: i64,
}
```

`edge_hash_blake3` hashes the first and last 1 MiB plus file size. It detects common replacement or truncation without reading a many-gigabyte file in full. A full-content checksum is intentionally excluded from V1.

The UI state machine is explicit:

```text
Empty
  -> Probing
  -> Ready <-> MarkingDeleteStart
  -> Review
  -> Exporting
  -> ExportComplete

Any operational state -> RecoverableError -> previous safe state
```

Only one project and one export job can be active in V1.

The video area and timeline are the primary workspace. The interval list is a navigator and status list, not a clip bin.

### 3.3 Opening a source

1. The empty screen presents one primary action: `打开录屏`.
2. The file dialog filters for `.mp4` but permits selecting any file to produce a useful unsupported-format error.
3. Rust canonicalizes and authorizes only the selected path.
4. ffprobe reads container and stream metadata.
5. The app validates one supported video stream and zero or one primary audio stream.
6. The app computes the source fingerprint and looks for an existing project.
7. If a matching project exists, offer `继续上次进度` or `重新开始`.
8. If path matches but fingerprint differs, block automatic resume and explain that the source changed.
9. The selected file is exposed to the WebView through a narrowly scoped local asset URL.
10. Loading must not copy or pre-transcode the source.

### 3.4 Playback

- `Space`: play or pause.
- `Left` / `Right`: seek by 1 second.
- `Shift+Left` / `Shift+Right`: seek by 5 seconds.
- `Cmd/Ctrl+Left` / `Cmd/Ctrl+Right`: seek by 30 seconds.
- `J`: reduce playback speed.
- `K`: pause.
- `L`: increase playback speed.
- Supported speeds: 0.5×, 0.75×, 1×, 1.25×, 1.5×, 2×.
- Clicking either timeline moves only the playhead.
- Scrubbing never changes markers.
- Use `requestVideoFrameCallback` when available to synchronize the playhead with displayed media time; fall back to a bounded timer.
- Seeking displays a busy indicator if the platform decoder needs time to reach the requested frame.

H.265 support on Windows WebView2 is conditional. On load failure, V1 shows a dedicated diagnostic with codec, platform, and instructions for installing or repairing the Windows HEVC Video Extension. It must not claim that the file is corrupt until ffprobe and an FFmpeg decode test also fail.

### 3.5 Marking delete intervals

- `I` or `[`: set the start at the current displayed media time.
- While a start is pending, the timeline shows a striped red region from the start to the playhead.
- `O` or `]`: close the interval at the current displayed media time.
- If end is not later than start, reject the command and keep the pending start visible.
- `Esc`: cancel a pending start.
- A completed interval immediately becomes solid red and is persisted.
- Overlapping or adjacent intervals merge deterministically.
- Selecting an interval reveals only left and right handles.
- Dragging the interval body is disabled; the cursor communicates that it cannot move.
- Boundary drag is clamped against zero, source duration, and the opposite boundary.
- Arrow keys adjust a selected boundary by one source frame; Shift+Arrow adjusts by one second.
- `Delete` removes the selected marker and therefore restores that source time.
- `Cmd/Ctrl+Z` and `Cmd/Ctrl+Shift+Z` undo and redo domain commands.
- Creating, resizing, merging, removing, undoing, or redoing invalidates review status for affected joins.

### 3.6 Timeline behavior

V1 has two synchronized timelines:

- **Overview:** always displays the full source duration. It is used for orientation and coarse seeking.
- **Detail timeline:** displays a zoomable window around the playhead. It is used for accurate boundary placement.

The overview may use a canvas because hundreds of intervals are cheaper to render as primitives than DOM nodes. The detail timeline may also use a canvas with DOM overlays only for the selected interval's handles and accessibility labels.

No waveform or full-filmstrip thumbnail cache is generated in V1. Tick density changes with zoom. At high zoom, frame ticks are computed from the normalized output frame rate.

### 3.7 Review mode

`检查并导出` first enters Review; it never starts exporting immediately.

Review mode shows:

- Source duration
- Total deleted duration
- Expected kept duration
- Number of joins
- Estimated output size range
- Output codec and selected encoder
- Source compatibility warnings
- Available disk space and required headroom
- A checklist of every delete interval

For each interval:

1. Seek to three seconds before the delete start.
2. Play until the delete start.
3. Virtually jump to the delete end.
4. Continue for three seconds.
5. Show the last retained frame before the cut and first retained frame after the cut.
6. Let the user mark the join reviewed or return to editing.

The virtual preview may contain a seek pause; it is a semantic preview, not a final encoded preview. V1 does not generate a temporary review movie.

All joins should be reviewed before export. The application may permit an explicit `仍然导出` override, but it must show the count of unreviewed joins and require a second confirmation because private content is part of the motivating use case.

### 3.8 Export interaction

1. The user chooses a destination MP4 path.
2. The source path is never an allowed destination.
3. If the final path exists, ask before export; never overwrite it directly.
4. The app creates a unique sibling path such as `.课程01.spycut-<job>.partial.mp4`.
5. Export locks edits and records an immutable export snapshot.
6. The UI shows overall progress, current phase, elapsed time, estimated remaining time when stable, and a cancel button.
7. FFmpeg runs with `-nostdin`; the application supervises it and never leaves an interactive process waiting.
8. Cancellation terminates the child process, waits for exit, and removes only the job's known partial file after confirmation that the process is closed.
9. A progress watchdog reports `可能卡住` after a bounded no-progress interval and offers cancel; it does not silently kill a healthy long disk operation.
10. On FFmpeg success, ffprobe and a short decode validation run against the partial output.
11. Only a validated file is atomically promoted to the chosen final path.
12. Completion shows output path, duration, size, codecs, elapsed time, and `在 Finder/资源管理器中显示`.

## 5. Non-functional requirements

### 5.1 Performance

- File size support target: at least 50 GiB MP4.
- Source duration support target: at least 6 hours.
- Application memory must be asymptotically independent of source file size.
- The UI thread must not perform file hashing, ffprobe parsing, FFmpeg execution, or project writes.
- No deliberate operation may block the UI event loop for more than 100 ms.
- Playback should use the platform's hardware decoder when available.
- Export should use a tested hardware encoder when available.
- Export uses sequential source reading and one final output; no full-size intermediate segment set.
- Timeline rendering should remain interactive with 1,000 normalized delete intervals.
- Logs and preview caches are bounded and cleaned by age/size.

### 5.2 Reliability

- Project edit recovery point objective: no more than one accepted command.
- Project recovery time objective: under five seconds after application restart, excluding source media load.
- JSON writes use temporary-file, flush, and replace semantics.
- A project migration function exists from schema version 1 onward, even though only V1 initially exists.
- Child processes are tracked by job ID and always reaped.
- Development/test commands use finite timeouts; app-launched FFmpeg uses `-nostdin`, progress supervision, and explicit cancellation.
- A partial export is never presented as a completed movie.

### 5.3 Privacy and security

- No network access is needed for normal use.
- No analytics, crash upload, or update check in V1.
- Content Security Policy denies remote scripts and remote media.
- JavaScript cannot execute arbitrary commands or choose arbitrary executable paths.
- FFmpeg arguments are passed as an argument vector, never as a shell command string.
- Only the user-selected source and destination are dynamically authorized.
- Logs contain paths only when needed for diagnosis and never contain frame pixels, audio samples, or extracted private text.
- The source is opened read-only.

### 5.4 Compatibility

V1 acceptance matrix:

| Container | Video | Audio | V1 behavior |
|---|---|---|---|
| MP4 | H.265 Main 8-bit | AAC | Required |
| MP4 | H.264 High/Main 8-bit | AAC | Required |
| MP4 | H.265 Main10 | AAC | Probe and capability-test; supported when platform encode path passes |
| MP4 | H.264/H.265 | No audio | Required |
| MP4 | H.264/H.265 | Decodable non-AAC | Re-encode to AAC with warning |
| MP4 | Other video | Any | Reject with detected codec |
| MKV/MOV/WebM | Any | Any | Reject in V1 |
| MP4 | Multiple video tracks | Any | Use primary track only after warning |
| MP4 | Multiple audio tracks | Any | Use primary track only after warning |

V1 normalizes precise-mode output to a constant frame rate derived from the source's reliable nominal rate. Strongly variable-frame-rate input is accepted only after displaying the chosen output rate; the export validator checks duration and audio/video drift.

This is a modular monolith. There is no local HTTP API, server, database, background daemon, or message broker.

### 6.1 Source of truth

Rust owns the authoritative `ProjectSession`. The frontend stores only a projection needed to render. Every edit is a typed command:

```text
AddDeleteInterval
ResizeDeleteInterval
RemoveDeleteInterval
SetPlayhead
Undo
Redo
MarkJoinReviewed
```

Rust validates, applies, persists, and returns/emits the updated projection. The frontend must never locally invent a normalized interval list that later conflicts with Rust.

### 6.2 Concurrency model

- `AppState` contains a short-lived lock around session metadata, not around file or process work.
- Probe, fingerprint, export, and validation run as async tasks.
- Each job has a cancellation token and unique ID.
- No lock is held while awaiting FFmpeg, ffprobe, disk I/O, or frontend events.
- Job events are monotonic and include the job ID so stale events cannot update a newer screen.

## 7. Media preview design

### 7.1 V1 approach

Use HTML `<video>` inside the Tauri WebView. Do not decode video in Rust and send raw frames across IPC.

For a 4K YUV420 frame, raw payload is roughly 12 MiB; at 30 fps that is roughly 360 MiB/s before IPC and GPU upload. RGBA approaches 1 GiB/s at 4K30. A Rust-to-JavaScript frame pipeline conflicts with the low-resource goal.

The frontend sends only playback commands and time values. The WebView owns decode and display. Rust provides the authorized local asset URL and media metadata.

### 7.2 Capability flow

1. `canPlayType` provides an early hint.
2. Attempt `loadedmetadata` and `canplay` with a bounded timeout.
3. If that fails, run an FFmpeg decode probe against a short source region.
4. Distinguish:
   - platform WebView lacks decoder;
   - FFmpeg cannot decode source;
   - source file cannot be read;
   - container metadata is damaged.
5. On Windows HEVC WebView failure, guide the user to the HEVC Video Extension requirement.

### 7.3 Future-compatible interface

Frontend playback code depends on a `MediaPlayerAdapter` interface rather than direct scattered DOM calls. V1 implements `HtmlVideoAdapter`. A future native libmpv adapter may replace it without altering project or export modules.

```ts
export interface MediaPlayerAdapter {
  load(sourceUrl: string): Promise<void>;
  play(): Promise<void>;
  pause(): void;
  seekTo(seconds: number): Promise<void>;
  setRate(rate: number): void;
  currentTimeSeconds(): number;
  dispose(): void;
}
```

## 8. Precise export design

### 8.1 Why V1 does not smart-render only boundary GOPs

Boundary-only H.265 re-encoding must join new and copied GOPs while keeping VPS/SPS/PPS, codec profile, level, pixel format, color metadata, time base, B-frame ordering, and MP4 sample description compatible. Different software or hardware encoders may emit incompatible parameter sets. A file may play in one player but fail or show artifacts in a professional editor.

V1 prioritizes exact cuts and output stability. It emits one continuous video stream from one encoder session.

### 8.2 V1 processing model

1. Sequentially demux and decode the complete source once.
2. Normalize source timestamps to start at zero.
3. Select only frames whose timestamps fall within derived keep intervals.
4. Renumber selected video frames to a continuous constant-frame-rate timeline.
5. Select corresponding audio and renumber samples continuously.
6. Encode selected video with one chosen encoder session.
7. Encode audio to AAC.
8. Mux one MP4 output.

The full source must be decoded because FFmpeg processes one sequential input, but only retained content is encoded. This avoids opening the same large file dozens of times, concurrent decoder contexts, full-size segment intermediates, and codec-parameter concatenation.

### 8.3 Precision

- Video boundary precision: at most one source frame.
- Audio boundary precision target: at most one decoded audio frame; output audio is continuous and re-encoded.
- Delete semantics remain `[start, end)`.
- If a marker lies between source frames, the export plan reports the retained/deleted frame decision rather than pretending to achieve sub-frame precision.

### 8.4 Filter-graph strategy

For keep intervals `[0, 125.400)` and `[140.200, 300.000)` at 30 fps, the generated filter script is conceptually:

```text
[0:v:0]
setpts=PTS-STARTPTS,
select='gte(t,0)*lt(t,125.400)+gte(t,140.200)*lt(t,300.000)',
setpts=N/(30*TB)
[vout];

[0:a:0]
asetpts=PTS-STARTPTS,
aselect='gte(t,0)*lt(t,125.400)+gte(t,140.200)*lt(t,300.000)',
asetpts=N/SR/TB
[aout]
```

Production code writes a filter-script file in a unique job directory. It never interpolates an untrusted path into shell syntax. Times are formatted by Rust from validated integer microseconds with a locale-independent decimal separator.

The implementation spike must confirm filter behavior for non-zero source start times, B-frames, 29.97/59.94 fps, missing audio, and VFR input before this graph is considered stable.

### 8.5 FFmpeg invocation rules

Conceptual invocation:

```text
ffmpeg
  -hide_banner
  -nostdin
  -y
  -i <authorized-source>
  -filter_complex_script <generated-filter-file>
  -map [vout]
  -map [aout]                 # omitted when no audio
  <selected-video-encoder-args>
  -c:a aac
  <validated-audio-args>
  -progress pipe:1
  -stats_period 0.5
  <unique-partial-output>
```

Rules:

- Spawn directly with an argument vector; no shell.
- `-y` is allowed only because the partial path is newly generated and owned by the job.
- Always add `-nostdin`.
- Bound probe/encoder-test/validation subprocesses with timeouts.
- Export itself may be long-running but must publish progress, handle cancellation, and close its child before the app exits.
- Store stderr in a bounded rotating job log.
- Do not parse localized human prose when a machine-readable FFmpeg/ffprobe channel exists.

### 8.6 Progress

Output time alone can stall while FFmpeg scans a long deleted interval. Therefore V1 needs source-time progress as well as output-time progress.

The implementation spike must choose one verified method:

1. Add a low-rate progress branch to the filter graph that reports source PTS every five seconds; or
2. Use another stable machine-readable FFmpeg signal that exposes processed input time.

Overall progress is based on processed source time divided by source duration. Output duration and encoder speed are displayed separately. A 60-second absence of any input progress changes the status to `可能卡住`; it does not by itself declare failure.

### 8.7 Encoder selection

Encoder availability must be tested, not inferred from names listed by `ffmpeg -encoders`.

Priority:

| Platform | H.265 | H.264 |
|---|---|---|
| macOS | `hevc_videotoolbox` | `h264_videotoolbox` |
| Windows NVIDIA | `hevc_nvenc` | `h264_nvenc` |
| Windows Intel | `hevc_qsv` | `h264_qsv` |
| Windows AMD | `hevc_amf` | `h264_amf` |
| Fallback | audited software encoder | audited software encoder |

On first export or after FFmpeg/GPU-driver change:

1. Detect candidate encoder names.
2. Run a tiny, bounded real encode test.
3. Cache successful capability with FFmpeg version and machine identifier.
4. Select the same codec family as the source.
5. Preserve Main10 only if the full decode/filter/encode test passes; otherwise require explicit user acknowledgement of an 8-bit fallback.

V1 exposes `高质量` as one product-level preset rather than raw codec controls. A dedicated calibration task must determine encoder-specific arguments using real lecture recordings with small text. It must compare source/output text clarity, color, file size, editor import, and speed. Do not hardcode one quality flag across VideoToolbox, NVENC, QSV, and AMF because their controls are not semantically equivalent.

### 8.8 Output validation

Before promotion:

- ffprobe exits successfully and returns JSON.
- Exactly one expected video stream exists.
- Video codec matches the selected H.264/H.265 family.
- Audio presence matches the export plan.
- Duration is within tolerance of the planned kept duration.
- Start time is near zero.
- Packet/frame timestamps are monotonic enough for MP4 playback.
- A short decode of the beginning and end succeeds.
- A bounded decode around every output join succeeds.
- Output size is greater than a defensible minimum.

Validation failure leaves the final destination untouched, retains the diagnostic log, and offers to remove or reveal the partial file.

## 9. Persistence design

> **Superseded on 2026-08-12:** The app-data-only location below records the original V1 plan. Current behavior is defined by [`2026-08-12-source-sidecar-persistence-design.md`](2026-08-12-source-sidecar-persistence-design.md): the source-adjacent JSON is authoritative and app data is only a recent-project cache.

### 9.1 Location

Projects are stored under the application data directory:

```text
SpyCut/
├── projects/<project-id>.json
├── index.json
├── cache/frame-previews/
├── jobs/<job-id>/
└── logs/
```

Storing projects in app data avoids failure when the recording directory is read-only. V1 may add `导出项目文件` later, but sidecar project portability is not required.

### 9.2 Atomic write

For each accepted command:

1. Update the in-memory Rust model.
2. Schedule a short debounced save.
3. Serialize to UTF-8 JSON.
4. Write a sibling temporary file.
5. Flush and synchronize as supported.
6. Replace the prior project atomically or with the safest platform-specific replace primitive.
7. Update the project index only after the project file succeeds.

On save failure, keep the session active, display a persistent warning, and retry after subsequent edits; do not claim the project is safe.

### 9.3 Undo/redo

Undo history is session-only in V1. Persisted project state is the latest materialized result, not the command log. A maximum of 100 commands bounds memory. Restart restores content but not undo history.

## 10. Error and failure handling

| Failure | User impact | Required behavior |
|---|---|---|
| Source missing | Cannot resume | Ask to locate file; verify fingerprint |
| Source changed | Privacy/accuracy risk | Block export; open as new or explicitly relink |
| H.265 unsupported by WebView | No preview | Explain HEVC extension/platform issue; do not call file corrupt |
| FFmpeg absent in dev | No probe/export | Show resolved search paths and setup action |
| Bundled sidecar missing | Packaging defect | Fatal diagnostic with app version/target triple |
| Hardware encoder unavailable | Slower or blocked export | Try verified next candidate; disclose fallback |
| Disk space insufficient | Export would fail | Block start based on estimated output plus safety margin |
| Disk fills during export | Partial output | Close process, keep final untouched, explain cleanup |
| FFmpeg hangs/no progress | Export stalls | Warn at 60 s, offer cancellation, save log |
| User cancels | No final result | Terminate/reap child, remove owned partial, unlock project |
| App crashes during edit | Recent state risk | Recover last atomic project file |
| App crashes during export | Orphan partial | Detect job directory at next launch; offer cleanup/reveal |
| Validation fails | Unusable output risk | Do not promote; retain report and partial by choice |
| Output already exists | Overwrite risk | Ask first; still write unique partial then safe replace |
| Chinese/spaces/quotes in path | Invocation risk | Use argument vectors and generated files; test explicitly |

## 11. Security design

### 11.1 Tauri permissions

- Use an explicit V1 capability file.
- Dialog access is allowed only for open/save flows.
- The frontend cannot invoke arbitrary shell commands.
- FFmpeg/ffprobe sidecars are invoked from Rust only.
- No generic filesystem read/write plugin scope is exposed to JavaScript.
- The asset protocol dynamically allows only the current selected source.
- Remote navigation and window creation are denied.

### 11.2 Content Security Policy

The CSP must allow application assets, the Tauri IPC transport, and the selected local media URL while denying remote scripts, remote frames, and arbitrary connections. Exact directives are verified on both WKWebView and WebView2 during the scaffold task.

### 11.3 Path safety

- Canonicalize source and destination in Rust.
- Reject a destination resolving to the source.
- Reject directories as movie outputs.
- Create the partial file in the final destination directory so final promotion stays on the same filesystem.
- Never use user input as an executable name.
- Never pass arguments through `sh -c`, `cmd.exe /C`, PowerShell command strings, or equivalent.

## 13. Test strategy

### 13.1 Rust unit tests

Mandatory interval cases:

- Empty delete list returns one full-duration keep interval.
- One middle delete returns two keeps in original order.
- Delete at zero returns no zero-length leading keep.
- Delete ending at duration returns no zero-length trailing keep.
- Overlaps merge.
- Contained intervals merge.
- Exact adjacency merges.
- Invalid negative or reversed intervals are rejected.
- Boundary resize cannot invert an interval.
- Delete-all blocks export.
- 1,000 intervals normalize deterministically.
- Undo and redo reproduce exact project states.

Mandatory persistence cases:

- Project JSON round-trip.
- Unknown schema version rejected safely.
- Corrupt JSON leaves a recoverable error and does not overwrite it.
- Atomic replacement preserves the prior valid file on injected write failure.
- Source fingerprint matches unchanged file and rejects changed first/last blocks.

Mandatory export-plan cases:

- Filter times use locale-independent decimals.
- Half-open semantics are preserved.
- No shell metacharacter from a path enters the filter expression.
- Missing-audio plan omits audio mapping.
- 29.97 and 59.94 rational frame rates are preserved.
- Planned duration equals the sum of keep durations within one frame.

### 13.2 Frontend tests

- Shortcut dispatch respects focused text/control elements.
- Interval body drag does nothing.
- Handle drag sends resize command only.
- Overview/detail coordinate conversions round-trip within one pixel.
- Pending start is visible and `Esc` cancels it.
- Review state shows unreviewed count.
- Export screen ignores stale events from a prior job ID.
- Time formatting handles more than one hour.
- Error banner differentiates WebView HEVC failure from FFmpeg decode failure.

### 13.3 Media integration fixtures

Generate finite synthetic files with FFmpeg:

- H.264 MP4, 30 fps, AAC, visible timecode/frame number
- H.265 MP4, 30 fps, AAC, visible timecode/frame number
- H.264 30000/1001 fps
- H.265 60 fps
- Video without audio
- Non-zero container start time
- VFR sample
- Main10 sample when local hardware supports it
- Chinese/space/quote characters in filename

Each fixture is short. Long-file performance uses real recordings rather than spending hours generating artificial H.265 media.

Integration assertions:

- ffprobe parse is stable.
- Exact marked content is absent within one-frame tolerance.
- Output duration matches planned retained duration.
- Output begins near timestamp zero.
- Audio remains present and within drift tolerance.
- All joins decode.
- Result imports into the user's target professional editor.

### 13.4 Manual acceptance media

Before calling V1 complete, test at least:

- One real three-hour H.265 lecture on Apple Silicon Mac
- One real H.264 lecture on Mac
- One real H.265 lecture on Windows with HEVC extension
- One real H.264 lecture on Windows
- At least one 4K source
- At least one source larger than 10 GiB
- A project with more than 100 delete intervals
- Cancellation during export
- Forced disk-space failure using a safe bounded test volume or quota
- Application restart after simulated interrupted export

## 14. Acceptance criteria

V1 is accepted only when all are true:

1. Opening a 10+ GiB source does not copy it and does not make memory usage proportional to file size.
2. The original file hash/size/mtime remain unchanged through the complete workflow.
3. A user can mark at least 100 delete intervals without clips or interval bodies being movable.
4. Restart restores the normalized interval set and last playhead.
5. Exported joins occur within one source frame of requested video boundaries.
6. No marked interval appears in the output under the defined half-open semantics.
7. Output chronological order is identical to the original.
8. Output H.265/H.264 codec family matches the source unless the user explicitly accepts a fallback.
9. Output opens in at least QuickTime/VLC on Mac, a standard Windows player with codecs available, and the user's professional editor.
10. Audio/video drift remains within one video frame at the end of the output for required CFR fixtures and real acceptance media.
11. Cancel, encoder failure, validation failure, and disk-full conditions leave the source and pre-existing final output untouched.
12. No child FFmpeg/ffprobe process remains after completion, cancellation, application exit, or failed validation.
13. All automated tests pass on macOS and Windows CI/runners selected for the project.

## 16. Architecture decision records

### ADR-001: Use Tauri 2, Rust, and Svelte

**Status:** Accepted

**Context:** The app needs one codebase for Windows/macOS, a lightweight UI shell, safe local state, and reliable control over FFmpeg processes.

**Decision:** Use Tauri 2 with Svelte/TypeScript for UI and Rust for authoritative state and all privileged operations.

**Consequences:** UI development is fast and the application avoids bundling Chromium. H.265 preview behavior depends on WebView platform codecs, and a future native player may require platform-specific integration.

**Alternatives:** Qt/C++ offered more uniform native media integration but a higher C++/Qt development and licensing burden. Electron had higher runtime footprint and did not solve HEVC distribution cleanly.

### ADR-002: Model only delete intervals

**Status:** Accepted

**Context:** Movable fragments are the user's primary source of mistakes in general editors.

**Decision:** Persist only source-time delete intervals; derive kept intervals and order.

**Consequences:** Reordering and timeline gaps are impossible by construction. The tool intentionally cannot support general editing without a new domain model.

### ADR-003: Use continuous precise re-encoding in V1

**Status:** Accepted

**Context:** Keyframe stream-copy shifts boundaries; H.265 boundary-only smart rendering has codec-parameter and editor-compatibility risk.

**Decision:** Sequentially decode the source, select retained frames, and encode one continuous output stream.

**Consequences:** Cuts are frame-accurate and output is stable, but export consumes encoder time and introduces one generation of high-quality lossy compression. Only retained frames are encoded, but the complete source is decoded.

**Alternatives:** Keyframe copy was rejected for multi-second boundary error. Boundary smart rendering is deferred until real-media evidence supports it.

### ADR-004: Use HTML Video for V1 preview

**Status:** Accepted with capability gate

**Context:** Sending decoded frames through Tauri IPC is too expensive; native libmpv embedding adds platform code.

**Decision:** Use the operating-system WebView video pipeline and explicitly diagnose unsupported HEVC playback.

**Consequences:** Low implementation cost and direct hardware decode on supported machines; Windows H.265 needs an available HEVC decoder path.

### ADR-005: Use versioned JSON project storage

Superseded by the 2026-08-12 source-sidecar persistence design linked in section 9.

**Status:** Accepted

**Context:** A project contains small structured state for one source and does not need queries or concurrency.

**Decision:** Store versioned atomic JSON in app data.

**Consequences:** Easy recovery and inspection; no database operational cost. Undo history is session-only.

### ADR-006: Run FFmpeg/ffprobe as supervised sidecars

**Status:** Accepted

**Context:** Media processing is complex, long-running, and can fail independently of the UI.

**Decision:** Spawn pinned external binaries from Rust with narrow arguments, machine-readable progress, cancellation, and validation.

**Consequences:** Crashes are isolated and debugging is simpler. Packaging and license compliance must be handled per target architecture.

- Use non-interactive installer flags.
