# 播放与定位竞态修复设计

## 问题与目标

正常播放、暂停和时间轴拖动会同时驱动同一个 HTML `<video>`。当前适配器直接暴露 `play()` Promise，并为每次精确定位独立等待 `seeked`；上层拖动开始会暂停，拖动结束又无条件恢复播放。因此，一个尚未完成的播放请求被后续暂停取消时会作为错误展示，连续定位也可能让旧请求等待错误的事件并触发固定五秒超时。修复必须保持源时间轴、删除区间和导出流程不变，只收敛预览命令并区分“被新操作取代”与真实失败。

## 方案选择

可选方案一是在 UI 里过滤英文错误并延长超时，改动最小，但仍保留并发 Seek 和失败后恢复播放。方案二是在 `HtmlVideoAdapter` 内实现 latest-wins：暂停使待完成播放请求失效；新的预览或精确定位使旧精确定位以“未完成”正常返回；只有当前请求才能消费 `seeked` 或报告超时。方案三是在 `App.svelte` 建立完整播放状态机，覆盖面最大，但会把底层媒体事件细节继续堆入页面。采用方案二，并让 `PlayerPane` 把定位是否完成传回页面。

## 数据流与错误处理

`play()` 记录请求代次；如果后续 `pause()`、加载或销毁使该请求过期，仅吞掉浏览器表示主动取消的 `AbortError`，权限、格式和解码错误仍上抛。`seekTo()` 返回 `boolean`：到达目标返回 `true`，被更新操作取代返回 `false`，当前请求在有限时间内仍处于 seeking 才抛出“视频定位超时”。目标时间按视频元素实际时长再次约束。拖动提交或取消只有在返回 `true` 时保存位置并恢复原播放状态；失败或被取代时保持暂停，避免错误链式覆盖。

## 验证

单元测试覆盖主动暂停打断播放、真实播放失败、精确定位被下一次定位取代、预览定位取代精确定位、丢失 `seeked` 但媒体已经停止 seeking，以及仍在 seeking 的有限超时。组件测试验证 `PlayerPane` 只在当前定位完成后派发时间。最后运行前端类型检查、完整 Vitest、`git diff --check`，并复核没有改动预览服务、项目持久化或导出路径。
